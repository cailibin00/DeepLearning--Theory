## 大模型的内存开销
首先我们来学习一下基本的内存知识。

- 训练：
`总内存 = 参数值 + 梯度 + 前向传播激活值 + 优化器状态 + 临时缓冲区`
- 推理：
`总内存 = 参数值 + 临时缓冲区 + 前向传播激活值`


### 参数值
和模型的参数数量有关，还和参数的精度有关，如果FP32那么x4，FP16则x2

$$占用内存 = 参数量 * 参数精度 / 1e9$$
### 梯度
占用内存和参数一样，精度也一样


### 前向传播激活值
也就是模型所有层的所有输出，是用来反向传播之后计算梯度使用的。

是根据模型的架构计算的。和batch size ， sequence length相关。

### 优化器状态
==这部分存在错误，涉及到量化的知识，请见谅==

| 优化器               | 状态/参数 | 总倍数 | 说明      |
| ----------------- | ----- | --- | ------- |
| SGD               | 0×    | 1×  | 只有参数本身  |
| SGD with Momentum | 1×    | 2×  | 保存动量    |
| Adam              | 2×    | 3×  | 一阶矩和二阶矩 |
| AdamW             | 2×    | 3×  | 同Adam   |
| Adagrad           | 1×    | 2×  | 梯度平方累积  |

### 临时缓冲区
通讯缓冲区、中间计算结果。

### MapReduce
![MapReduce示意图|600](file-20251103150404046.png)
- 这里使用文本的计数这个场景来讲解
1. Input：用户输入的文本，有很多行
2. Split：用户输入的文本按照不同的行切分成不同的部分
3. Map：一个部分对应一个 **Mapper/worker** ，计算一个单词出现的次数（分而治之思想）
4. Shuffle：取Mapper的结果，挑选不同的单词进入不同的**新的worker**（分而治之思想）
5. Reduce：**整合拼接**Worker的结果
6. Finalize：输出得到最终结果

![示例图2|600](file-20251103150948228.png)
- 这里使用文本索引的例子，读者可以根据上述思路
1. Input
2. Split
3. Map
4. Shuffle
5. Reduce
6. Finalize

- 总结MapReduce框架
首先，我们有用户进程，它需要协调或者定义我们程序怎么运行，它会先想数据有多少，需要拆解成多少个Mapper，多少个Reducer去做。比如要找5个Mapper去做，就会把数据拆成5份，这样会产生出很多很多Worker，会有Map Worker和Reduce Worker。

但最重要的是还会产生一个**Master Worker**，这个和其他Worker等级是一样的，只不过会做一些特殊事情，它会作为用户的代理来协调整个过程，用户就可以做其他事情。Master Worker会让这个Worker去拿0号数据，一个Worker负责拿1号数据等等，这就是分配数据的过程。

每个Worker会在本地把数据切分开吧，写到本地的缓存或者硬盘上行。前面Map Worker做完了，Master让Reduce Worker去拿数据，他们就会从各个Worker里拿到本地需要的数据，在本地做完Reduce以后将结果写到最终的文件里就是Finalize。实际上，这个过程可以看到第一步切数据是Input，第二步是Map拿数据Split，第三步自己切分就是Map，第四步Reduce去拿数据是Shuffle，第五步Reducer自己去做数据的整合是Reduce，第六步输出结果Finalize。

## Data Parallelism
分为两个类别，Ring All-Reduce 和 Parameter Server，这都和分布式通信原语密切相关。

作为第一个概念，我们介绍一些简单的东西

$$time = 数据规模 * 单步计算量 / 计算速度$$
$$计算速度 = 单设备计算速率 * 设备数 * 多设备并行效率$$
- 其中，设备数并不是越多越好，还和数据的规模，还有服务器的架构有关。

在Data Parallelism之中，需要解决的问题是不同batch在多卡上计算的梯度汇集问题，我们假设第一个GPU是服务器。
### Ring All-Reduce
我们说着很容易，reduce scatter,all to all，但是要高效实行是需要严格的算法的。

- Ring：首先要明白，这个模型之中GPU是线性连接成一个环的。每一个GPU有一个从下一个GPU的输出接口，从上一个GPU的输入输入接口。
- All-Reduce：该算法只需要执行两次循环，就可以完成**All Reduce**的操作

- 感性理解：因此，随着GPU数量增加（例如一个），样本数量增加（卡越多能够处理的样本越多），但是完成通讯只需要线性增多（每个GPU增多1x2次）。并且，在这样的安排下，**每个设备的入口带宽和出口带宽都被用上了**，而且不会发生争抢带宽的事情。
- 定量分析：假设带宽为β，总样本数为V，GPU数量为p
$$time = \frac{V(p-1)}{p\beta}$$
$$data\_each\_gpu = \frac{V(p-1)}{p}$$

## Pipeline Parallelism
这一块就是讲模型按照不同的layers，放到不同的卡上，前面是拆分数据集，这里是拆分模型。


我们首先明确两个训练策略：
1. 同步训练：多个批次同时出发，需要等到所有计算停止之后，得到平均值来更新模型
2. 异步训练：多个批次同时出发，先计算完的批次先更新模型

异步训练：优点是减少了等待时间，但是不同批次使用不同的迭代，造成了“落后”，后更新的批次计算的梯度版本存在偏差，可能现有的模型已经不适用该梯度了，可能造成无法收敛。

### Gpipe
![Gpipe|600](file-20251103234747196.png)
我们首先看最原始的b，注意一个细节，最慢完成训练的卡最先完成梯度的更新，这是反向传播的特点。

图中空白的地方表示设备空闲的时间，我们把它叫做空泡。我们致力于减少他。
我们试图使用并行化来减少空泡，思想就是在后面模型跑的时候，前面的模型也在跑，但是这不能在相同的数据上实现，因为数据是串行的，那么只能在不同的数据集上体现了。

因此，我们要利用**时间差**，把不同的批次不同时间送入，那就是图c，这样就缩小了泡泡，实现了串行。，当然也就意味着，送入的数据越零散，我们的空闲时间越少，当然这也是有极限的，我们计算出来，设备的空转率是：

$$\frac{n(n-1)}{n+m-1} ，m是批次数量，n是卡数$$

得到结果，分的批次越多越好，m极限的时候无需等待，当然n越少越好，因为分的卡越多，意味着初始的等待时间越多，当然我们还要考虑设备的内存使用率，显然要做一个平衡。

值得注意的是，我们的梯度是最后一起更新的，也就是**同步更新**。

### ZeRO-DP
我只将这一个分支，因为其他的我看不懂

简单来说，我们重新回到大模型的开销部分，我们纠正了前面优化器的错误

1. 假设模型有a参数，那么按照FP16，则占2a内存
2. 梯度存储占2a内存
3. 优化器AdamW：FP32备份4a，FP32一个动量一个二阶动量，一共8a，

那么一共占用 2a + 2a + 12a = 16a。我们这远远大于我们模型本身的参数，扩大了 8倍，深表遗憾。

重点就在优化器上，他占用了大头，我们想将他均匀分散。

### Optimizer State Partitioning
基于Data Parallelism的框架。我们有N卡，我们就把优化器状态分散到N卡上，实现了≈4a极限的占用内存。

现在每一个卡上有完整模型，我们前向传播的方向传播一次，这个卡拥有自己数据的梯度
1. 适用reduce scatter获得每一个部分的平均梯度，每一个卡只有一个部分的完整梯度，通讯记作b
![300](file-20251103204812849.png)
2. 利用梯度更新自己部分模型的参数，无通讯
3. 将优化后的模型状态all gather分发到多个卡上，通讯b

总的来说，通讯2b

### Gradient Partitioning
我们发现了，有些梯度的存储多余，我们不需要用All gather梯度，因此，我们用不同的卡负责不同的梯度维护。

实际上这和我们前面讲的一样，暗含了不需要将梯度all gather的思想。

通讯2b

### Parameter Paritioning
我们用不同的卡维护不同的模型部分，其他的参数完全不存储，这部分要求我们通讯模型参数，保证参数不会落后于最新版本

1. 前向传播+反向传播，都需要将现有的模型参数all gather到所有卡，用2b
2. 反向传播得到了对应的梯度，只需要reduce scatter，就可以巧妙地将每个模型地部分和每个部分的梯度对应起来，用了1b
3. 梯度更新只需要原地更新，因为我们可以使得优化器维护部分和模型维护部分重叠，无通讯
4. 不需要all gather模型，因为我们适用分发模型而不是每张卡维护全量模型

只需要3b通讯


因此，我们结合了g,p,o三种方式，最终完成了所有参数的分配，并且通讯录保持在DP（data p..）的1.5倍，很好，开心。
