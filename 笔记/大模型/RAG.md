我们直接从高级RAG开始学习（Advanced RAG）

RAG是检索增强生成，原理：给模型一个数据库，用户提出问题的时候，模型从数据库中查找出对应的资料，在提示词中融合资料，输出回答。RAG解决的问题是，模型本身训练的参数尽管有知识，但是还不足以满足用户广泛的询问需求——因而会造成幻觉。但是我们不能通过不断地增大训练集来解决问题，因此，我们要使用将文本作为输入来完成模型知识的填充，这类似于我们的few-shot。可以看到，很多大模型的改进思路是很相同的。

RAG的难点：检索技术。

下面我们简单讲解原始RAG的内容，然后转向进阶的技术

## 原始RAG
![原始RAG|600](file-20251113170215421.png)

### 数据库构建
收集已有的文本，作为原始的数据库。

收集到的文本要进行 **分块**，意义在于我们后面要将这些资料输入提示词，模型的上下文有限，不能直接将全文塞进去。

### 编码
一般将文本（chunk）编码成为单个的向量。

他是chunk的高级维度表示，压缩了信息，浓缩了语义。我们会将所有chunk的编码存储起来，并且建立索引关系。


### 检索
RAG的核心，编码chunk的目的是为了让我们索引出合适的文本作为输入。那么同样的，我们要使用相同的编码器对用户的Query进行相同的编码表示。

将Q和chunk的编码进行相似度比较，选择**top k**，然后索引到原始文本，原始文本充当context输入提示词，相似度计算可以有很多
1. **余弦相似度**
2. 点积
3. L1（绝对值
4. L2（MSE


## 高级RAG
我们大可以吐槽传统RAG
1. 索引效率慢
2. 文本分块粗暴
3. 信息作为上下文粗暴
4. 编码细粒度不够

下面我们来解决问题

### 数据库的构建问题
涉及到文本分块

- 按照固定长度截断：容易把语义破坏（一般不使用）
- 按照固定符号截断：比如文本分段，或者文本分句子，按照规定字节访问选择句子数量。一般搭配**句子重叠**，重叠相当于挽回了一些被截断的语义，但是也会引入杂质，但是仍然是该手段的管用挽救办法
- 使用语义分析的模型，判断上下文是否语义相同（花销比较大）

chunk的大小还和模型的上下文长度有关，需要动态调整。但是太小又会破坏语义，比较难搞。


### 编码
我个人很喜欢假设性问题
#### 假设性问题和HyDE
涉及到语义的对齐问题，更加专注用户查询和文本之间的语义问题，思想类似于CoT：
1. 将每一个chunk通过LLM，**生成一个问题**
2. 问题再编码嵌入成为向量

解决了查询和文本之间语义的偏差，使用LLM纠正了语义，再进行相似度计算，很妙。


同样的，我们为何不将用户查询先假设生成一个答案，再用`Query + pre-Answer` 编码Q，和chunk计算相似度，也就是 **HyDE**。我的评价
1. 纠正了语义
2. 生成的pre-Answer没有数据库的知识，处于知识匮乏状态，我们的目的是优化这个Answer，现在再使用匮乏的回答和丰富的知识去相似度计算，我觉得这并不能找出对的检索文本，反而加剧了回答的**错误性和多样性**。


### 检索问题
我个人比较喜欢融合检索
#### 传统做法
- **使用关键词筛选**：
1. 寻找用户查询中的关键词
2. 在数据库中直接查询

缺点：
1. 无法凝练语义信息（没有使用到编码）
2. 杂质太多，没有筛选的手段

- **全量搜索**：
1. 计算量太大
2. 用户查询的语义和chunk语义的对齐问题

#### 分层索引
- 做法：
1. 减少了计算量，核心就是将n个chunk进行summary，**得到一个chunk摘要向量**，浓缩了几个chunk的信息
2. chunk还要进行传统的逐个chunk编码
3. Q向量首先和summary向量进行相似度计算，选择K个摘要，再从K个摘要中进行全量搜索，减少了时间复杂度
![分层索引|600](file-20251113172621187.png)

- 缺点：
1. 额外储存摘要向量
2. 摘要向量语义训练存在难题，并且部分chunk的归属摘要，使得少量语义相关的chunk被同一个摘要中的多数不相关覆盖

尽管缺点，这还是一个朴素的优化办法


#### 融合检索
通过语义搜索可能导致部分缺漏，那我们就再**加上关键词搜索**，也就是生成最大的可能关联性集合，再后续通过重排序对于该最大集合筛选，就能够减少缺漏的可能性。


### 数据增强
传统的就是直接将chunk塞到提示词中，忽略了
1. chunk的文本可能质量不高，需要 **过滤**
2. chunk的文本被截断，需要补齐
#### 语句窗口检索
![窗口检索|500](file-20251113174153659.png)
朴素说，就是检索到的chunk加上前后n个chunk，一起作为输入

#### 父文档检索
是更加详细的处理，会预设分组，一个组有n个chunk

收集到了原始chunk，在每一个组中统计是否有大于m个chunk入选，有的话就送入整个组。

这是在窗口检索的基础上多了一部数量筛选。

### 重排序和过滤
这是检索之后的处理，获得检索后的chunk还不足够。需要检索后优化。

在检索的时候，我们大概会生成50个chunk，但是在输入提示词时候只会输入5-10个，这个时候需要在检索的基础上排序，再输入。而原始的相似度分数，可能由于我们的 **混合检索**，或者语义不精准，导致效果不佳。

那么我们需要对于已有的文本进行重新排序，那就当然需要额外的模型，额外的计算量。

我本人比较喜欢cross-encoder + 元数据
#### cross-encoder排序
输入`[CLS] query [SEP] chunk1 [SEP]`，相当于编码器交叉注意力，利用CLS标记来评分，输出的是0-10的相关性分数。

#### LLM辅助排序
顾名思义，利用现有大模型API来得到分数。不需要重新训练模型

综上所述，这一步是优化我们性能的很好一步，但是需要我们 **收集监督数据，训练排序模型**，是一个比较难搞的步骤。


#### 元数据过滤
在这里，过滤和排序其实很相似，都是选出最佳的chunk输入。但是过滤的手法更加粗糙一点。

我们的数据存在一些独特的属性记录，例如 **日期，作者，来源**。我们可以通过简单判断筛选掉过期的，不喜欢的作者等的信息来源。


### 重写
其实这并不是一个技术，我将他用来归纳。这也是我最喜欢的一个改进技术。

#### 文本重写
这部分在“编码”一部分中讲到了，是将文本重写成为问题，来纠正分布


#### 查询重写
1. 有时候面对复杂的查询，一个查询向量往往不能表达成为合适的语义信息。这个时候需要一个LLM，将初始查询分成多个小查询，再在数据库之中查询，我在使用豆包的过程中发现了这个 **做法**。

![查询重写|600](file-20251113201055211.png)

- 解释：本质上还是CoT，对于问题的推理，拆分成多个点慢慢解决，形成了更长的**推理链条**。同时能够链接到更长的相关性文本，有利于推理。

2. 还有一种办法，利用LLM来写出一个**更好的查询**。
#### 评价重写
也就是后文讲到的，在评价文本相关性时，将回答重写成为问题，然后计算相关性。

#### 输入重写
我有听说过将输入的chunk重写的技术，但是目前没有找到参考资料，这也是一个好的办法吧，不过token数有点多了。

## 评价指标
我们总结一下我prefer的高级RAG所需要的模型
1. 假设性问题 —— 普通的LLM
2. embed —— 假设性问题的编码
3. cross-encoder —— 重排序的模型
4. 最终的文本输出 —— LLM

其中第一点可以使用一个独立的LLM小模型来实现，不需要训练。
第二点是RAG的关键，我们可以使用类似于CLIP的对比训练来实现。
第三点需要监督数据。
第四点需要判断模型是否真的根据RAG来回答问题。

我们重点讲第二点和第四点

### 检索环节

#### 准确率
不必多说，我们输出的topk中有多少个命中了目标

#### 召回率
和准确率实际一样，描述我们的预设的m个预期chunk中有多少个**被命中**了


#### 平均倒数排序MRR
$$MRR = \frac{1}{Q} {\sum_{i=0}^{Q} \frac{1}{rank_i} }$$
- Q是相关查询的数量
- $rank_i$ 是第i个查询中，真实第一相关文档在检索中的排序

场景：假设首次检索之后
```
1. a
2. b
3. c
```
但是重排（认为是相关性的正确排序）之后结果为
```
1. b
2. c
3. a
```

那么此时，我们相关性第一是b，在检索中的排序是2，所以  $MRR = 1/2$ 

如果有多个查询，就计算之后平均，效果最佳表现为MRR = 1 。 这是信息检索之中的一个常见指标。


### 生成环节
这边和大模型的输出评价相差不大，不过多了与RAG信息的近似程度。

成熟的评价体系给出了下面两个标准：
1. **答案基于性**：答案是否由检索上下文支撑（对应忠实度）。
2. **答案相关性**：答案是否解决用户问题（对应答案相关性）。
#### 文本相似性
这就需要监督文本来评价了。


#### 答案基于性
把回答拆分为句子。

$$基于性得分 = 有上下文支持的句子数量 / 答案总句子数量$$

可以使用cross-encoder模型来评判。

这个标准衡量了是否回答是否每句话都有依据，能够改善 **幻觉**。
#### 答案相关性
衡量生成答案是否直接、完整地回应用户问题，评估 "答非所问" 程度，关注内容匹配而非事实正确性。
- 解释一下：前面相关性是答案是否基于知识库，这很好理解；相关性则注重与用户端，用户接收到的信息是否吻合**用户的提问**，因为模型可能因为知识库而忽略了用户的回答。

- **反向生成问题法**：这是我最喜欢的办法
他类似于假设性问题。初衷是计算回答和问题的相似性。
那么我们使用和假设性问题相同的模型，利用回答生成一个基于回答的问题。再将问题编码成为向量。
1. 直接：向量和Q计算相似度
2. （笔者创新）在假设性问题的 拓展间接：向量和被选中的chunk计算相似度，间接代表了Q，同时也能够 **计算答案基于性**，妙极了！！

当然，Q可以生成多个，然后通过直接法求平均，就是代表性的相关性了。


### 总结
我们需要在两个关键步骤评价RAG的表现，我perfer：平均倒数排序 + 答案相关性 + 创新的答案基于性。

需要使用的模型：编码时期相同的生成问题的普通小参数LLM，和嵌入向量编码模型，无需训练新模型。
